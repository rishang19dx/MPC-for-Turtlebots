# Project plan — NMPC trajectory tracking for TurtleBot3 Burger

AR-521 Control for Robotic Systems · end-semester project · solo · 14 days

## Confirmed intent

| | |
|---|---|
| **Outcome** | ROS 2 Humble package: CasADi/IPOPT nonlinear MPC on a unicycle model that tracks reference trajectories (circle, figure-8, Lissajous, sinusoid, random splines, point-to-point with variable start/goal) and avoids LiDAR-detected static obstacles via MPC constraints. Same node runs in Gazebo and on the real TB3 Burger. |
| **Graded on** | Report + demo video + viva. Rigorous baseline comparison and Monte Carlo quantification matter most. |
| **Success** | (1) NMPC vs Kanayama, Samson/backstepping, kinematic SMC under identical saturation/rate/state. (2) Paired Monte Carlo over random start/goal/trajectory/obstacles with statistics. (3) ≥1 filmed hardware run with honest drift analysis. (4) Full modelling + formulation + ablations (N, weights, DC vs CBF γ). |
| **Constraints** | Solo, 14 days, limited lab time, odometry-only localization, MPC on laptop over Wi-Fi at 10 Hz. |
| **Out of scope** | Moving obstacles (stretch), mocap, learned dynamics, Nav2 global planner, multi-robot, onboard solving. |

Research backing every design decision: [`reports/TurtleBot3 NMPC tracking design.md`](reports/TurtleBot3%20NMPC%20tracking%20design.md).

## Architecture

```
            ┌──────────── laptop ────────────────────────────────┐        ┌──── TB3 Pi ────┐
 /scan ───► │ obstacle_extractor ──/obstacles──┐                 │        │                │
 (5 Hz)     │  (segment → circle fit → tf2)    ▼                 │        │                │
 /odom ───► │                     mpc_controller (10 Hz)  ──/cmd_vel_safe──► cmd_vel_relay ─► /cmd_vel
 (~20 Hz)   │   delay comp → NMPC | Kanayama | Samson | SMC      │  Wi-Fi │ (0.3 s timeout,│
            │   (+ CBF-QP safety filter for baselines)           │        │  e-stop)       │
            └────────────────────────────────────────────────────┘        └────────────────┘
```

* `tb3_mpc/core/` — **ROS-free**, pytest-tested: model, saturation, references, controllers, NMPC, CBF filter, LiDAR circle fitting, kinematic simulator, metrics.
* `tb3_mpc/nodes/` — thin rclpy wrappers.
* `experiments/` — Monte Carlo benchmark (multiprocess, kinematic sim) + analysis/plots.

## Three-tier evaluation

1. **Kinematic Python sim** (same `core/` code) — statistical bulk: ~30–50 paired seeds × families × controllers × perturbations.
2. **Gazebo** (headless, p3d ground truth) — confirmatory subset + obstacle scenarios.
3. **Hardware** — demo runs, taped ground truth, measured latency/odom rate.

## Hardware-day checklist (days 9–10)

- [ ] `export TURTLEBOT3_MODEL=burger LDS_MODEL=LDS-02 ROS_DOMAIN_ID=<unique>` on Pi and laptop; same RMW
- [ ] Dedicated router / hotspot with multicast; verify `ros2 multicast send/receive`
- [ ] chrony: laptop as server, Pi as client; check offset < 5 ms
- [ ] `ros2 topic info -v /cmd_vel` → Twist or TwistStamped? set `stamped_cmd_vel` param
- [ ] `ros2 topic hz /odom`, `/scan`; check invalid range encoding (0 vs inf)
- [ ] Robot still during boot (gyro calibration); calibrate wheel radius with 2 m tape drive
- [ ] Start `cmd_vel_relay` on the Pi **before** anything else; test e-stop and Wi-Fi-unplug stop
- [ ] Velocity step test `python3 experiments/hw_step_test.py --v 0.15` → dead time τ, lag, /odom & /scan rates; set `delay_compensation` accordingly
- [ ] Tape start/end poses; film from a fixed overhead-ish angle

## Viva talking points to prepare

- Why multiple shooting; why 1−cos heading cost; why penalise u − u_ref
- Terminal cost only — gap between Gu & Hu theory and implementation, stated honestly
- DC vs CBF: why DC grazes obstacles, why CBF is myopic-safe, feasibility, slacks
- Kinematic backstepping ≡ Samson law (don't claim 4 distinct baselines)
- Why baselines get a CBF-QP filter in obstacle runs (fairness)
- Where NMPC loses (smooth references, small offsets, model mismatch) and why that's fine
